Memory: a project knowledge section served by Bench

A proposal, not an approval. It recommends turning reference/ and the reviews Bench already files into one browsable, linkable section of the board, and bounds a first delivery. Nothing described as proposed exists yet; addresses such as /memory/… are illustrative until implemented.

1. A worked example

◔ review PR on #147→report filed on the card→Memory lists it→link pasted into #152→read weeks later

  1. Bench completes a review. Juno's PR review of card #147 ends with PR REVIEW: APPROVE at head 4f0ae65. Exactly as today, the board appends the report to the card under ## PR review at 4f0ae65 (current) — 2026-11-14 10:02 (Juno) and records Bench's verdict. New: the same filing step marks the review published, and the card's Reviews round carries In Memory with a Read in Memory link (mockup 3).
  2. The ticket links to the report. The card's Activity line for the filing says published to Memory and links to the page; the page links back to the card's Reviews.
  3. Someone finds it later. Ronald opens Memory in the header, filters to Reviews and card #147, or searches “one click” (mockup 1).
  4. Someone follows a pasted permalink. Card #152's brief says “see /memory/147/rv-3c9a51e07b”. The page opens on any machine that reaches the board (mockup 2) and says at the top that it approves 4f0ae65, not whatever #147's branch holds now.
  5. Nothing was copied. The card and the Memory page render one report. If the filing failed, neither shows a verdict and the failure is visible with a retry (mockup 5).

3. Naming and information architecture Recommended

LabelForAgainst

ReferenceNo rename at all.Names a folder of attachments, not a place you read reviews and decisions.

Recommendation: the header view is Memory. Context keeps its current meaning: the selected information supplied to a task or run. reference/ keeps its name and role as attachment storage; it is not renamed or moved.

4. A section inside Bench Recommended

  • Navigation. A seventh view in the header switcher, after Settings, at /memory. Same build, same access, same addresses scheme as the other views; no second service, port or login.
  • Board and card. A card's Reviews round gains In Memory and Read in Memory; its Activity line for the filing links to the page; a Linked from Memory list shows entries that name the card. The Memory page links back to the card's Reviews. (mockup 3)
  • Delivered outcomes. A delivered card's reviews stay in Memory; their pages say the card is Done and what they were about. Show-the-result outputs stay machine-local artifacts and are linked, not copied (see §9).
  • The Activity bar's file list keeps working and gains a “Browse in Memory” link.

5. Content types, browse and search Recommended

Six kinds, deliberately few: Review (PR and relevance), Investigation, Decision, Guide, Prototype and Attachment (a file adopted from reference/ or plans/ with no richer description). Tags, hierarchies and spaces are Later at most.

  • Browse: newest first, one row per entry — kind, title, one-line summary, source card, date, applicability (mockup 1).
  • Filter: kind, applicability (current, historical, superseded, unclassified) and source card.
  • Search: a substring match over title, summary, card number, review id and file name, computed over a small server-built index. No embeddings, no summarisation model.
  • Empty and no-results states say what fills Memory and offer the next step: adopt the existing files, write a guide, clear a filter (mockup 5).

6. Identity, permalinks and two-way links

Recommended An address names what the thing is, never where its file sits:

  • A review: /memory/<card number>/<review id>, e.g. /memory/147/rv-3c9a51e07b. Both parts already exist and are stable: card numbers are for life, and the id is a hash of the heading line the board wrote once.
  • A guide, decision, investigation or prototype: /memory/e/<slug>, where the slug is written once in the entry's header and kept when its title changes.
  • An attachment: its existing /files/reference/<name> address, unchanged, plus /memory/e/<slug> once it has a catalogue entry.

What happens when things change:

EventThe link
Card moves stageUnaffected: resolved by number, as /cards/<n> is.
Card archivedStill opens; says the card is archived and links to its read-only view.
Card or entry renamedUnaffected: neither address carries the title.
Guide revisedThe address shows the current revision; ?rev=<n> shows an earlier one, read from git.
Entry or file deletedA tombstone page: what it was, who removed it, what replaced it. Never a silent 404.
Address never existed, or from another boardSays not on this board, like a card address does.
Old reference/ links in cards and reportsKeep working byte for byte; nothing is moved. Memory shows the file's entry beside it.
Two cards share a numberAs for cards: listed, each by its file stem.

Two-way: a card lists entries that name it (Linked from Memory), computed by reading entries' **Card:** header and links, never by writing into the card.

7. Publishing reviews automatically

Recommended One report, two views. The card's history stays the single authoritative store of a review's report, as it is today. Memory does not copy it: the review page is a rendering of that section, addressed by card and id. Consequences:

  • When. A review is published the moment its report is appended to the card — the same write that exists now, for both relevance and PR reviews. There is no second step that can half-succeed with a different text.
  • Consistency. The ticket and the page cannot disagree, because there is one text. Neither is editable; a verdict is never altered. A later round is a new report.
  • Failure. Today a report that cannot be filed (card moved boards, card gone — task 148) is narrated in the ticker and kept in the run's log. Proposed: record it as an unfiled report (machine-local, beside the run), shown on the card and in Memory with Retry filing (mockup 5).
  • Retry and idempotence. A retry re-files the same text under the same heading; the heading is the identity, so a report already present is a no-op, never a duplicate.
  • Index lag. If Memory's search index is stale it is rebuilt from cards; the page itself always reads the card, so “filed but not yet listed” is temporary and harmless.
  • Provenance on the page: card, review kind and round, reviewer and model, filing time, assessed head and base with the authority each was read from, brief revision, the evidence ids bench recorded (labelled local to the board that ran them) and whether GitHub took a formal review. Where the board that renders it does not have the machine-local records, the page says so rather than guessing.

Owner decision The PR-review heading carries the assessed commit; relevance reviews currently record no brief revision in theirs. Recording it (as the Reviews tab already wishes) is a small change to the heading or a record line and is recommended.

8. Historical reports, maintained knowledge Recommended

  • Reviews and investigations are snapshots. Immutable, dated, bound to what they assessed. Their page leads with that binding. A past approval never reads as approval of current code: if the card's branch has moved, the page says so in the warning register and links to the card's current state. Superseded rounds say history — an earlier commit.
  • Guides and decisions are maintained. Revisable, with an owner, a revision number and an applies to line. Edited by a person, committed to the work repository like any board edit; their history is git's.
  • Supersession is explicit. An entry names what it supersedes (**Supersedes:**); the older page wears Superseded by … and is not edited.
  • Ownership. Agents produce snapshots only. Maintained entries are written by people (an agent may propose one through a card, as refinement does). Bench never rewrites a maintained entry by itself.

See the contrast in mockup 4.

9. Storage, sync, index and adoption

Recommended

  • Reviews: stay in card files (already in the work repository, already synced with BOARD_COMMIT_MOVES/BOARD_SYNC). Nothing new to store.
  • Maintained entries: one Markdown file each in a new flat <work root>/memory/ directory, with a card-style header (**Kind:**, **Slug:**, **Card:**, **Applies to:**, **Supersedes:**, **Owner:**). Flat for the same reason plans/ is: the current file handler and listing are flat, and flat names keep links simple.
  • Attachments: stay in reference/. A catalogue entry in memory/ describes one and links it.
  • Index: computed by the board from the cards (including archive/), memory/, plans/ and reference/, memoised by the work-state head like the movement reading. Not committed, so it cannot conflict.
  • Rendering: Markdown through the page's existing renderer; HTML, SVG and PDF through the existing /files/ route with its sandbox.
  • Shared versus local. Shared (committed): cards with their reports, memory/, reference/, plans/. Local (never committed): verdict records, evidence and logs, review checkouts, kept artifacts, unfiled reports, the index. A review page on a teammate's board shows the shared report and says which local facts it does not have. Copying runtime evidence into the work repository is not recommended: it holds this machine's paths and can be large, which is why it was made local.

Adoption of existing material is conservative and explicit: nothing is moved, renamed or rewritten. Memory lists every existing plans/ and reference/ file as an Unclassified attachment from day one. A person may then adopt one — write its catalogue entry with a kind, title, summary and card — individually or in a reviewed batch whose preview lists every file it writes. Old links never change.

10. Access, safe rendering and agent context Recommended

  • Same access as the board. Memory is a view of the board, behind the same loopback binding, Host and origin checks. No public exposure, no separate service, no share-outside links. A permalink grants nothing: whoever opens it reaches it only if they already reach the board.
  • Untrusted content. Reports and entries are rendered by the existing renderer (raw HTML as text, only safe link schemes, images as links). HTML and SVG attachments open only through the sandboxed /files/ route; the sandbox and script-src 'none' are not relaxed for Memory.
  • No secrets or transcripts. Only filed reports are published. They are already capped and marker-quoted by reports.py; the proposal adds the credential scrubber (redact.py) on the way into the card. Session timelines, raw logs and pinned inputs are never published.
  • Retaining is not delivering. Being in Memory gives no run any access. A run still reads only its approved context and its card's declared inputs, pinned and hashed; the readiness check still decides. A future “use as input” action would write an Inputs line on a card for a person to confirm — Later.

11. The mockups

Five static pages, served by the board exactly as any plans/ HTML is: no script, inline styles, real links between pages, <details> folds and a CSS theme switch (Night is the default; Daylight appends #day). Controls marked simulated do nothing. Each page has a narrow layout under 760px.

  1. Library — landing page with entries, kinds, source cards, search and filters (daylight)
  2. Review page — summary, verdict, provenance, assessed commit, applicability, permalink (daylight)
  3. Ticket Reviews and Activity — how a new report is reached from its card and back (daylight)
  4. Guide vs historical review — maintained knowledge beside a superseded snapshot (daylight)
  5. Empty, no results and failure — with recovery actions (daylight)

How to open: on a board whose work root holds this package, open /files/plans/151-memory-proposal.html (this page), or the index 151-memory-index.md from the Activity bar's plans/ list. Screenshots at 1280px and 390px, night and day, are kept by the browser check that verified this package (see §15).

12. Options and the recommended first delivery

Minimal incrementRecommended first deliveryLater
User valueReviews and files become findable and linkable.That, plus guides/decisions with applicability, adoption of existing files, visible publication failure.Revision diffs, “use as input”, cross-board views, richer taxonomy.
ScopeMemory view listing reviews (from cards) and existing files; review pages at /memory/<n>/<id>; card ↔ page links.Minimal + memory/ entries with header fields, supersession, tombstones, search/filter, unfiled-report record and retry, adoption flow.Embeddings, summarisation, collaborative editing, separate wiki service — only if evidence shows a need.

MigrationNone.None forced; adoption is opt-in per file.—
Cost and riskSmall: one module, one route family, one view. Risk: index cost on large boards (memoise).Medium: an editor for entries (reuse the refine/brief write path), a new parser with the card-header rules.High, and mostly unproven value.

Recommendation: deliver the recommended first delivery in two cards — the minimal increment first (it is useful on its own and changes no storage), then maintained entries and adoption. Keep reviews in cards; do not build a second report store.

Alternative considered — reports as separate files. Writing each review into memory/ and leaving a pointer on the card would make Memory self-contained, but it moves the authoritative record out of the card that acceptance.py, the Reviews tab, delivery and the PR body read today, adds a two-file write that can half-fail, and doubles the sync surface. Not recommended for the first delivery.

13. Implementation breakdown

Reusable contracts: the review headings and ids (acceptance.py ROUND_RE, relevance_id); card reading and the archive (taskfiles); the /files/ route and its sandbox; the page's Markdown renderer and report presentation; the address table and router (task 134); the browser-mutation door for writes; the work-state commit path for board edits; redact.py.

  1. Backend reading — a memory.py core module (above taskfiles and acceptance in the layer table) that builds the index and resolves one entry; GET /api/memory and GET /api/memory/entry, read-only.
  2. Front end — the Memory view (library, reading page), its addresses, and the card integration (Reviews chip and link, Activity link, Linked from Memory), coordinated with #149.
  3. Publication failures — the unfiled-report record in agents.py's filing path, and a retry route behind the browser-mutation door.
  4. Maintained entries and adoption — the memory/ format, an editor using the board's write-and-commit path, supersession and tombstones, the adoption preview.
  5. Documentation — AGENTS.md section, the address table, the website docs; browser cases for each view and state.

Coordination with #149. #149 owns how a card presents its information; this proposal owns the project-wide library and reading page and only adds the entry points on the card shown in mockup 3. Whichever lands second adapts to the other's Reviews layout; neither should redesign the other's surface.

15. How this package was verified

A browser case (verify/browser_cases/case_memory_proposal.py in the bench repository, run by bench's bench-browser check) starts a disposable board from the candidate's own manager/core, copies this package into its work root, and opens every page at its real /files/plans/ address in sandboxed Chromium. It checks the served headers (type, nosniff, the sandbox policy), that no page overflows at 390px, that every static link between pages resolves to a 200, that keyboard focus reaches the links and is visible, and takes the screenshots in both themes. Limitations: fonts fall back to system fonts (a sandboxed page cannot load the board's Plex files); stylesheets must be inline because .css downloads; the theme choice does not carry across links; everything marked simulated is inert.
